# Test-driven acceptance: CAOS Mineral Plant Explorer workbench

These are product acceptance tests, not only code checks. A test fails if a different area selection leaves the same complete asset/stream diagram on screen.

## A. Model and graph tests

| ID | Acceptance test |
|---|---|
| TDD-01 | Every required area ID exists; each required core asset is assigned exactly once; all authored assets are assigned to an area or explicitly classified as shared context. |
| TDD-02 | For each area, the selected asset set is strictly smaller than the global set where appropriate, and its internal stream set differs from every other detail area. Boundary streams resolve to explicit connector nodes; dangling IDs fail validation. |
| TDD-03 | Water view includes every stream with a positive `water_m3_h`, including streams whose material is slurry, solution or electrolyte. It labels m³/h and never treats internal recycle as an external input. |
| TDD-04 | Water-balance closure is unavailable when any required boundary/value is missing, stale, invalid, or unit-incompatible. No missing value is imputed as zero. |
| TDD-05 | Plant snapshot and all engine observations retain asset/stream identity, units, source, version/hash, provenance and timestamp. Incompatible or stale adapter data is refused or visibly unavailable. |

## B. View behavior tests

| ID | Acceptance test |

| TDD-12a | Global and each of the nine area scopes produce a distinct 2D spatial site plan, process schematic, and 3D scene. Selecting an area replaces the complete global composition with the selected area's own detail and updates its title, boundaries, assets, KPIs, data and linked integrations. | TDD-12b | 2D site plan represents spatial arrangement: meaningful site zones/footprints, authored roads/shared services, per-area equipment placement, local spatial connections, orientation and selection. At global scale it preserves plant context and density; area detail enlarges that area and exposes its assets and boundaries. It cannot degrade to a row of cards, an ID list or a process flowsheet. |
| TDD-12c | Process schematic represents material/process logic: equipment-kind symbols with ports, clearly directed stream routing, stream/material and valid rate/unit labels, local recycle, named inter-area connectors, boundary input/output terminals and text labels and area-specific process guide. The required area coverage is asserted separately for mine extraction, crushing/stockpiling, grinding, flotation, leach/SX/EW, thickening/filtration, water balance, tailings and utilities. |
| TDD-12d | Both global and scoped 3D scenes show recognizable equipment at the intended camera scale, authored site/process context and stable asset selection. Every equipment class must have deliberate, legible geometry; one or two good meshes do not satisfy plant-wide quality. Global camera fits the full model; area camera fits the selected area's assets and declared boundaries while hiding/de-emphasizing unrelated geometry. | TDD-12e | At 1440×900 and 390×844, each mode retains its own composition, headings, legend, selection, source/provenance and relevant KPI/context. Text does not collide or clip. Screenshots for each scope/mode are reviewed for density, hierarchy, readability, spatial truth, process routing, symbol quality, equipment geometry and information completeness; geometry-only checks cannot satisfy this row. |
| TDD-14 | Each area information panel shows its purpose, input/output boundaries, relevant source-supported metrics, related streams, linked CAOS evidence and trends. Every number has a source, timestamp/time basis, unit and evidence class. Unsupported KPIs are absent. |
| TDD-15 | Replay motion animates only valid flowing streams in the selected view; pausing stops it; no ambient spin or continuous decorative pulsing; reduced-motion disables nonessential animation. |
| TDD-16 | With no real gateway configured, the app states synthetic replay. A configured live source labels source, freshness and quality; stale, bad and missing inputs are visibly unavailable. |
| TDD-16a | Hovering/focusing an overview area reveals its useful preview; activating it from the global overview opens the selected area's detailed process page. The page contains the selected area's own graph, boundaries, equipment and area-specific information. Keyboard activation works. |
| TDD-16b | Opening an area from a global 2D plan keeps the 2D plan active and replaces its global spatial composition with the selected area's spatial composition. The same rule holds for schematic and 3D views; URL, area selector, equipment list and view label agree. Returning to Whole plant opens the global overview. |
| TDD-16c | Selecting an area filters CAOS engine links and method-comparison channels to its core assets; the water-balance scope uses its participating water-bearing assets. Global scope retains all evidence, and areas with no bound engine show an explicit empty state. |
| TDD-16d | In each area schematic, stream labels do not overlap equipment, boundary terminals or other labels; boundary labels stay within the diagram viewport. Process and site-plan views do not render area tiles as cards connected by generic lines. Oversized diagrams scroll horizontally and show a visible scroll hint. The browser geometry sweep requires the expected core equipment count (or expected water-participating area count), verifies the 22 water-linked assets in the global 2D plan, exercises global-overview drill-down, confirms per-area 2D compositions and detailed schematics in English and Spanish, and checks mobile scroll and page overflow for all 18 language/area combinations. | TDD-16e | 3D equipment labels separate asset identity from the current value. | TDD-16f | Stream material families in boundary cards, internal schematic labels and area flow lists are localized in English and Spanish. Unknown future identifiers remain readable. `stream-material.test.ts` covers common and unknown material names. |
| TDD-16g | Each of the nine areas has non-generic English and Spanish process-reading content: its modeled route, at least two process-specific engineering checks and explicit evidence/boundary limits. The guidance is shown with the selected area's detailed schematic, agrees with the authored graph, and cannot label a synthetic reference as plant data. `areas.test.ts` covers completeness, localization, distinctness and key evidence boundaries. |

| TDD-16h | A direct area URL paired with `view=overview` or no view canonicalizes to that area's detailed schematic before rendering; area, selected asset, visible tab and URL remain synchronized after direct navigation and browser back/forward. |
| TDD-16i | Focus is a purposeful re-composition, not the ordinary view with headers/context removed. It preserves app/page identity, active view title, area name, legend and provenance. The shell title carries the drawing title; duplicate site-plan caption may collapse to give the clickable spatial plan room. The drawing/scene is the dominant central stage; a compact HUD shows up to four relevant, source-labeled KPIs. On phone, the visualization leads and the configuration panel remains reachable. The same weak/empty visualization with headings removed fails. Exit restores view, area, asset, time, language and theme. |
| TDD-16j | Adversarial browser checks open all six modes in all nine areas, then check Focus for every mode at desktop and phone widths. Focus equipment selection updates the selected drawing node and selected-data display; site-plan selection updates the rail summary without hiding the selected reading; moving replay time changes the selected process reading. Confirm the HUD does not cover clickable site-plan targets. Each view must render its mode-specific spatial, flowsheet, 3D, trend/availability or engine-evidence content. Run `npm run check:visual-modes -- <base-url>`. |

## C. Integration tests

| ID | Acceptance test |
|---|---|
| TDD-17 | Valid CAOS engine manifests are discovered and their outputs appear on the relevant area/asset. Source product, engine/version, hash, unit and evidence class are inspectable. |
| TDD-18 | Missing engine, missing artifact, hash mismatch, unsupported schema, unknown binding and incompatible unit each produce a named unavailable/incompatible state; they do not break other adapters. |
| TDD-19 | The read-only site adapter rejects HTTP except loopback development, invalid credentials, graph-revision mismatch, out-of-order values and future timestamps; it never exposes a write operation. |

## D. Browser/deployment gate

| ID | Acceptance test |
|---|---|
| TDD-20 | Browser matrix visits global plus every required area in all three representations; asserts distinct area IDs, node/stream sets, area content and per-view screenshots after every selection. |
| TDD-21 | Visual captures at desktop and narrow phone widths show a usable global view and all area views, legend, inspector, source status and no clipped primary interaction. English and Spanish labels work. Review layout balance, hierarchy, line crossings, label/card intersections, information density, value legibility, equipment form, camera framing and animation behavior. Passing geometric assertions alone is insufficient; a reviewer must inspect the rendered screenshots. |
| TDD-22 | The canonical HTTPS endpoint has a valid hostname certificate and enforced HTTPS. `/`, `/app`, data manifests and all SPA routes load the exact deployed commit; browser console has no uncaught errors. HTTP-only is a deployment failure. |
| TDD-23 | Release asset hashes and source tag match the exact deployed commit. The Zenodo GitHub integration produces exactly one software concept record for the current release. |
